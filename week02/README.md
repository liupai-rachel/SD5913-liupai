Why Am I Learning Programming?

I have never written a program before. So when I started learning programming in 2026, my first reaction was actually a question: why?

AI can already generate working code from a sentence. It can make a website, create an interaction, and even find and fix mistakes in code. As someone who is studying design rather than computer science, it is easy to think that learning programming now is a little backwards. If I can describe what I want and an AI can build it, why should I spend time learning how the code works?

I don't think the answer is that every designer needs to become a programmer. In fact, I expect the opposite. Designers may write less and less code in the future. But I think there is still a difference between being able to ask a machine to make something and being able to understand what you are asking it to make.

My background is in product design, but my practice has gradually moved across graphic design, UI/UX, service design, and HCI. What connects these areas for me is not a particular software or skill. It is the question of how people interact with things, information, and systems. This is also why programming feels relevant to me, even though I do not plan to become a programmer.

This became clearer to me when I worked on ‘Echoes of the City’, a project about how people explore the history and culture of Hong Kong. At first, it might look like a project about visual design or an interface. But the more I worked on it, the more I realised that the important questions were about the experience itself. When should a user receive information? What should happen when they arrive at a particular place? Should they read something, look at something, listen to something, or interact with it? How can historical information become part of the experience of exploring a city instead of just another piece of information on a screen?

These are design decisions. An AI could potentially help me implement them. It could generate the interface or write the interaction behind it. But it cannot replace the reason I chose one interaction instead of another.

This is where I think programming becomes relevant to me.

I don't see code simply as a technical skill that designers need to add to their CV. I see it as another material of digital design. A product designer should have some understanding of materials because materials affect what can be made. A graphic designer needs to understand visual elements because they affect how a message is perceived. In a similar way, when I design a digital system, I need at least some understanding of the logic underneath it.

Without that understanding, I can still describe what I want. I can tell an AI, “Make the interface respond when the user reaches this location.” But if I don't understand anything about how that response is triggered, what information the system needs, or what limitations the implementation has, I am depending entirely on the machine's interpretation of my idea.

That dependence matters.

AI is very good at producing plausible solutions. But a plausible solution is not necessarily the right solution. It can give me something that works while still missing the intention behind the design. This is especially important in HCI and service design, where a small change in timing, information, or interaction can change the user's whole experience.

For me, learning programming is therefore less about learning how to type code and more about learning how digital systems behave. I want to be able to look at an AI-generated solution and ask: Why does it work this way? What is it assuming? What can I change? What is causing this behaviour? Is there a better way to achieve what I actually want?

I also think this changes the meaning of authorship. If AI writes most of the code in a future design project, I don't think that automatically means the designer has stopped being the author. But authorship cannot simply mean choosing a prompt and accepting the first result. It has to include making decisions, understanding consequences, rejecting things that are wrong, and taking responsibility for the final experience.

So I am not learning programming because I believe I will write code faster than AI. I almost certainly won't. I am learning it because I don't want my relationship with AI to be “I ask, and it decides.” I want it to be closer to “I decide, and I use the machine to help me realise it.”

Maybe in the future I will rarely write a program from scratch. That is fine. If anything, that might make programming knowledge more valuable in a different way. I don't need to compete with the machine at producing code. I need enough understanding to know when the machine is helping me and when it is quietly designing for me.

That is why I am here.

I am here to learn enough programming to understand the medium I am designing with, so that even when AI becomes better at making things, I can still decide what should be made, why it should exist, and whether it is actually what I meant.
